# Changelog

All notable changes to Orkeon Studio are recorded here. Breaking changes come first in each release, with a migration table when one applies.

## Unreleased

Built against the Orkeon main that follows `1.3.0` (System One modes, the decision circuit everywhere, `effort: auto`, the tool bridge: Orkeon #438, #447), which no tag carries yet; this Studio does not build against the published `1.3.0`. Until that Orkeon is tagged, the branch builds against the Orkeon of pull request [#462](https://github.com/Orkeon/orkeon/pull/462) (commit `af992aaed`, untagged), packed into `dev-feed/`, a temporary source of `nuget.config`, with `OrkeonVersion` on that pack's local version; the closing commit removes `dev-feed/` and that source, and moves `OrkeonVersion` to the tag. No breaking change to Studio's own files; see Breaking and Changed for what the settings check and the launch now refuse. It needs the wire changes of that pull request (issues #448 to #461 and #464 to #468): the oracle and drift tests read that engine, and fail on an Orkeon without them. That pull request also fixes [#448](https://github.com/Orkeon/orkeon/issues/448), the watched run launched with « Use the decision models (System One) » switched off that failed before its first event when a decision provider was configured.

### Breaking

- **An enumeration written as a number is refused** ([#23](https://github.com/Orkeon/orkeon-studio/issues/23), Orkeon #464), as the engine's start now refuses it: a hand-written file that sets `"FailMode": "1"`, an account's `"Provider": 1` or `"Rights": "3"`, or a number among the names of a `[Flags]` list (`"Rights": "Read, 2"`) is no longer read as the member of that number. Write the names. A comma list where one name is expected is refused too, in the engine's sentence: a value, a list item, a dictionary value, a nullable and a `[Flags]` enumeration are each compared with the engine's own walk, and every e-mail and drive sentence with the engine's binder, `"Rights": "3"` included. Studio reports such a value and keeps it as written; it never rewrites it. In a section the engine walks it blocks the save (`"FailMode": "1"`: `STUDIO-SETTING-REFUSED`, an error); an account's numeric `Provider` or `Rights` is a warning (`STUDIO-MAIL-VALUE`, `STUDIO-DRIVE-VALUE`), the account's form showing no right granted.

| Written | Write instead |
| --- | --- |
| `"Rights": "3"` (e-mail) | `"Rights": "Read, Organize"` |
| `"Rights": "3"` (drive) | `"Rights": "Read, Write"` |
| `"Provider": 1` | the provider's name, for example `"Gmail"` |

- **A `Provider` under `Llm` or a model profile is refused unless it is `mock` with its `Responses` file or the key of a provider module** ([#20](https://github.com/Orkeon/orkeon-studio/issues/20), Orkeon #457), as the engine's start refuses it (`STUDIO-LLM-PROVIDER`, an error): a vendor of the catalogue (`openai`, `azure`, `custom`…) is picked by the address, never named there; a name no module answers, the mock without its file and a `Responses` beside another provider are refused too, in the engine's sentences. The `orkeon` tool registers no module yet. Remove the key, or write `mock` with its file.

### Changed

- **No refusal repeats a value its key cannot read** ([#21](https://github.com/Orkeon/orkeon-studio/issues/21), Orkeon #465): a switch, a number, an enumeration written as a number or as a comma list, `Orkeon:Guardian:Llm:Phases` written as a single value and the keys of an e-mail or drive account are refused in the engine's sentences, which name the key and what it takes, never the value, since a value of the wrong type may be an API key written by mistake. Nor does a refusal against a closed list of names, as the engine this branch builds against says it and Studio follows: a model's `Thinking` under `Llm:ModelCapabilities`, a decision stage's `Kind`, `Phase` or `Steps`, and a `Provider` under `Llm` or a profile and its `Responses` name the key and what it takes; only `Orkeon:Guardian:Llm:Phases` still quotes the phases it refused, to show the typo. The binder's refusal is said without its value even where the key path holds an apostrophe (a decision profile named `l'equipe`), and is filed at that key. A number that is not finite reads `<key> is not a finite number: write a number within the type's range.`, and the refusal of an account's `Rights` lists `None` among the names it takes, as the engine's binders do. The terminal editor's field errors and the caption of a switch whose file holds no boolean follow.
- **Step 1 of the team-creation wizard opens with a « Decision models » tab** ([#22](https://github.com/Orkeon/orkeon-studio/issues/22)): the System One block (the assistant's « compose without asking the decision models » switch, the mode the team asks of them, the session line and the warning) leaves the « Need » tab for a tab of its own, first of the step. Its subtitle says the mode shown, and it shows a warning when the machine cannot serve that mode. Step 1 opens on « Need », unless the mode of a resumed or reopened session meets something this machine cannot serve: it then opens on « Decision models », so that the warning is seen. Neither a composition nor a change of the decision settings moves the tab, and the guided tour's first stop selects « Need ». « Back » on « Need » leads to « Decision models ».
- **Every check box of the WPF app is a switch** ([#22](https://github.com/Orkeon/orkeon-studio/issues/22)): `Switch` is the implicit `CheckBox` style of `Themes/Studio.xaml`, the box keeps a key (`CheckBoxBox`) and no view sets a style on a `CheckBox`. The hints that said « tick » or « unticked » say « turn on » or « off », in the five languages, and a hint under a switch starts where the switch's label does. The rows of the team-folders modal and of the « Add an allowed folder » chooser are switch rows: the whole row toggles, with the switch's track and knob.
- **A settings file the engine's start refuses blocks « Launch now » and « Validate (dry-run) »** when it is the file the run reads (a pinned one, or the team's own): decision settings the engine refuses (`STUDIO-DECISION-PROVIDER`), a duplicate key, a decision profile or a value of `Orkeon:Guardian` its rules refuse and a profile name shared by `Llm:Profiles` and `Orkeon:Decision:Profiles` among them, the message naming the file to fix; a fail-closed LLM judge (`Orkeon:Guardian:Llm`) while the decision circuit is off; a value or a key the tool bridge's sections refuse; tools to bridge without their token (`STUDIO-BRIDGE-TOKEN`); a `Provider` the start refuses, under `Llm` or any profile (`STUDIO-LLM-PROVIDER`, a Danger alert of the Launch tab), which the terminal launcher makes an error of the launch and of a check, in the engine's sentence. While the CLI picks the file itself, the WPF app judges the machine's file and only warns.
- **« Launch now » is blocked for a crew the run would refuse**; the check stays offered. Such a crew needs the decision models while the circuit is off (`STUDIO-DECISION-REQUIRED`): it states `decision.mode: required`, holds `system_one_decide` under strict tools, or has a decision task without an answer. A decision provider without its key is an off cause like the others, for every need, since the engine then turns the circuit off (`no-key`, Orkeon #451) and refuses the run (exit code 69 for `required`): « <Provider> has no key (…), so the engine turns the decision models off: store the key in Settings › Decision models. » Blocked as well: a crew routed on `llm.profile: auto` without a ladder, or with a rung nobody provides (`STUDIO-DECISION-LADDER`); one that states `decision.mode: none` and names `auto` or a decision profile (`STUDIO-DECISION-MODE`); and one that names a fail-closed guarded decision profile while the circuit is off (`STUDIO-DECISION-PROFILE-BLOCKED`). The missing key also blocks a fail-closed guarded decision profile when the settings are the file the run reads (a warning on the machine's file), and warns that a lenient runner withholds `system_one_decide`; only a team that can run either way gets the plain key warning (`STUDIO-DECISION-KEY`).
- **The settings check reports more errors, so a file that saved before may be refused** (`STUDIO-SETTING-REFUSED`): a value the engine's start refuses and a key that is no setting, at any depth, in `Orkeon:Compaction`, its `Prune`, `Orkeon:Skills`, `Orkeon:Tools:Bridge`, `Orkeon:Bridge`, `Orkeon:Guardian`, `Orkeon:Decision` (a decision profile the engine refuses: no `Target`, no stage, an unknown stage `Kind`, a probability outside [0, 1]) and the decision providers' sections. A `ContextWindowTokens` that is not a whole number above zero is a `STUDIO-TYPE` error.
- **A missing decision key is named by its setting when the variable is not the provider's own** (Orkeon #467): an `Orkeon:<Provider>:ApiKeyEnvVar` that holds anything other than the provider's own variable is no longer repeated, since it may be a key pasted there by mistake; Studio says « the variable named by `Orkeon:Liquid:ApiKeyEnvVar` » instead, as the engine does.
- **The `Llm`, `Orkeon:Tools:Email` and `Orkeon:Tools:Drive` sections are judged whatever the letter case of their keys** (`llm`), as the configuration binds them; a write goes where the file spells the key.
- **A section that names its `Provider` gets no `STUDIO-LLM-ENDPOINT` notice** for a custom address without a path: the run builds that provider without reading the address.
- **The warnings of a missing decision key say what the engine does**: it turns the decision models off and sends the provider no request, the team running without them, no longer that every request fails (« … so the engine turns the decision models off and sends it no request: the team runs without them, … »), on the Launch tab, in the terminal launcher, in the description of `STUDIO-DECISION-KEY` and in the hint of the `system_one_decide` tool.
- **The diagnostics' model problem reads « No model is set up for the teams, or its settings need attention. »**, since `orkeon doctor` also warns there (a workspace for a provider that does not send it, Orkeon #468).
- **A model profile named `auto` is refused by the settings check** (`STUDIO-LLM-PROFILE-NAME`): the engine reserves the name for System One's pick of a profile and refuses to start with such a profile. Rename the profile, and the crews that name it.
- **A model's context window goes with its model.** When the default section or a profile gets another model, from the WPF app or the terminal editor, a `ContextWindowTokens` written for the previous one is removed.
- **Exit code 69 of `orkeon run` is read as a script or settings error** (a crew that requires System One, the decision circuit off), no longer as an unexpected code. The WPF app says it in a line of its own, in the five languages: the team cannot run without the decision models, and where to set them up.
- **In the terminal editor, Tab enters the section shown**: it walks from the section list through the fields to the buttons and back.
- **In the terminal editor, the lists of the RAG and LLM screens sit under their caption, on the whole width**, and a line that names something long of the file (a profile, the caption of a switch whose file holds no boolean) ends on an ellipsis instead of being cut by the edge.
- **The settings check refuses what the engine's start now refuses** (Orkeon #449, #450, #454, #455, #456), so a file that saved before may be refused (`STUDIO-SETTING-REFUSED`): a key written without a value (a JSON null, `{}`) on a switch, a number or an enum, in the engine's sentence, in place of what a rule said of the zero the binder would write; a single value where a list or a section is expected (a decision profile, its stages, a stage, `Orkeon:Guardian:Llm:Phases`, a model's entry under `Llm:ModelCapabilities`), unless the list takes a comma-separated value; a value inside a decision profile that does not convert (`"FailClosed": "maybe"`), which the binder dropped without a word; an enum written as a number (a guardian phase `2`); a blank switch of a model's capabilities; a `NaN` or infinite share. The computed `IsEnabled` and `IsDockerHostOverHttp` of `Orkeon:Tools:Bridge` are keys that are no setting. Each guardian threshold out of `[0, 1]` has its own sentence, its value in the invariant culture.
- **A switch of the context form written without a value** shows the `false` the binder would write and its refusal; the next apply writes what the field shows (a blank removes the key). The share fields of the Context compaction card ignore `NaN` and the infinities.
- **A forge error ends the trial when the engine says the process goes no further** (`terminal`, Orkeon #453), no longer when it is not recoverable: a spent budget ends the trial at once, an invalid edit asked again does not. The creation wizard raises its failure card for an unrecoverable error the engine says it stops on; an engine that does not write `terminal` is read as before. `recoverable` keeps saying whether the session can be resumed.

### Added

- **The Anthropic workspace** (`Llm:WorkspaceId`, Orkeon #468, [#25](https://github.com/Orkeon/orkeon-studio/issues/25)): the default and every profile carry the workspace an identity-linked Anthropic key acts in. The profile editor shows the field below the API key, in Novice and Expert alike, on an Anthropic address or while a workspace is set; the terminal editor on its `LLM` screen; a launch lays it as `ORKEON_Llm__WorkspaceId`, and the endpoint probe sends it as `anthropic-workspace-id`, as a run does. A workspace on another provider is a warning, `STUDIO-LLM-WORKSPACE`, with the run's remedy. A section without an address is judged too, its provider following from the model's name, then the key's prefix, else OpenAI (`gpt-4o` warns, `claude-*` does not); a section whose address the start refuses gets its endpoint error and no workspace warning, and one that names a provider other than `mock` is not judged.
- **The engine's own sentence of an off decision circuit is shown** ([#24](https://github.com/Orkeon/orkeon-studio/issues/24), Orkeon #467): when `run.decision` carries `detail`, the forge's `session.started` `forgeCircuitDetail`, or its `FORGE-DECISION-UNAVAILABLE` error `detail` (for `no-key`, the environment variable and the setting the key is read from, never the key), the run panel's circuit line and the wizard's assistant line follow Studio's translated sentence with it, in English as written (« the decision provider has no API key: …: no Liquid API key: set the environment variable LIQUID_API_KEY, or Orkeon:Liquid:ApiKey »), and the refusal's status line, failure card and report follow the engine's message with it, unless the message already says it. A blank `detail` is ignored, wherever it comes. An engine that writes none is read as before.
- **The decision circuit off for want of a key is said** (`no-key`, Orkeon #451): the run panel's circuit line and the wizard's assistant line read « the decision provider has no API key: set its environment variable, or its ApiKey in the settings », in the five languages; the forge's `FORGE-DECISION-UNAVAILABLE` error keeps its `cause`, and its message names the variable.
- **A pick or a pruning outside any task is listed under the agent's role** (Orkeon #460, #461): `agent.route`, `agent.effort` and `agent.pruned` without a `taskId` are kept, a route held to the ladder's `floor` or `ceiling` says so in a sentence of its own, and a level set for the first time is no raise.
- **A Decision models tab sets up System One** (Models group, both modes): the circuit's switch, the provider, and per provider its API address, model, timeout and retries, written in place in `Orkeon:Decision`, `Orkeon:TypeSafe`, `Orkeon:Liquid` and `Orkeon:Kev`. A provider's key goes to the user environment through the key store, never to the file.
- **The same tab sets what System One picks among**: the ladder of model profiles for `llm.profile: auto` (`Orkeon:Decision:Route:Ladder`) and the thinking levels for `thinking: { effort: auto }` (`Orkeon:Decision:Effort:Levels`). A rung that names no profile of the settings is a warning.
- **A status line says what a run of the file gets**, resolved as the engine resolves it, the environment's settings included: the provider named or deduced, none, or refused with the engine's reason.
- **The terminal editor gains a Decision models screen**: the provider, a tri-state switch, each provider's section with its model and address, the ladder and the levels. It stores no key, and refuses at apply an unknown provider name and a ladder or levels the engine refuses.
- **Studio reads what a crew asks of System One** with the engine's loader: the mode it states in `decision: { mode }`, or one deduced from its decision tasks, the `system_one_decide` tool and what it lets System One pick. A team's card carries a « System One required » or « System One optional » badge.
- **A launch can go without the decision models.** The WPF Launch screen offers « Use the decision models (System One) » to a crew that uses them, and switched off passes `--no-decision`; the terminal launcher always has a `--no-decision` box.
- **The launch says what the decision models change before it starts**: beside the refusals listed under Changed, a provider without its key, to a crew that can run without the models (`STUDIO-DECISION-KEY`), a tool the engine withholds and goes on without (`STUDIO-DECISION-TOOL-DROPPED`), and, for a crew that runs without the models, what answers each decision task and what stands in for each pick (`STUDIO-DECISION-FALLBACK`). One finding is said, the heaviest.
- **The run panel shows what the decision models answered.** A decision task's row gives, per question, the option chosen (or the score, or the yes), its probability and the model's confidence, or « no answer », in place of the raw JSON, which stays in the tooltip; a task its relay answered reads « decision (relay) ».
- **A « System One and context » panel lists what the run did around its agents' model calls**: the profile and the thinking level picked or kept, the skills carried, a context compacted, tool results pruned. It keeps 200 lines, the circuit's line among them, always the first; the other 199 are the latest. The circuit's line shows at once for a crew that states `optional` or `required`, for any other only once the run does something it explains.
- **The creation wizard chooses what a team asks of System One** (Orkeon [#431](https://github.com/Orkeon/orkeon/issues/431)). Three choices on the first step; « When available » and « Always » go to a new creation as `orkeon forge --crew-decision optional` or `required`, « No » passes nothing. A session keeps the mode it was created with; when the list shows the pick of the next composition instead, a line under it names the mode of the team on screen. A notice under the list says what the mode meets when the decision models are off on this machine; a decision provider without its key counts as off, so for « Always » it says that the trial will be refused.
- **The assistant can compose without the decision models** (Orkeon [#435](https://github.com/Orkeon/orkeon/issues/435)): a switch, « Compose without asking the decision models », passes `--no-decision` to each run of the assistant that composes, tries or resumes a creation, never to an adoption; when the settings switch the models off, it reads on and is locked, a line under it saying why. A line under the assistant's profile says whether it works with them, its calls on this run and the tokens they spent over the session.
- **A team that runs either way is tried twice**, with the models then without: the Try step names the pass under way, each line of the activity says its pass, the verdict card gives each pass's verdict, and the checklist shows each criterion by its worst finding across the passes.
- **The assistant's warnings reach the wizard's status line**, as the engine's code then its message, after the « ready » sentence when the run ends ready.
- **The compaction of a context, the pruning of its tool results and the skills are set in Studio**: two cards of the **Limits & index** tab (Expert), « Context compaction » and « Skills », and a **Context & skills** screen of the terminal editor, write `Orkeon:Compaction`, `Orkeon:Compaction:Prune`, `Orkeon:Skills` and the default model's `Llm:ContextWindowTokens`. Every field that has an engine default shows it: as a watermark in the cards, in brackets in the terminal screen.
- **A summary profile the file does not define is a warning** (`STUDIO-SETTING-REFUSED`), since a run launched from the WPF app is given Studio's own model profiles; the terminal launcher, which lays none, makes it an error.
- **The tool bridge is set in Studio** (Orkeon [#445](https://github.com/Orkeon/orkeon/issues/445)): two full-width cards of the **Limits & index** tab (Expert) and a **Tool bridge** screen of the terminal editor write the caller's `Orkeon:Tools:Bridge` and the serving `Orkeon:Bridge`. The token goes to the user environment through the key store, under the variable the section names, never to the file. Studio does not start `orkeon bridge serve` and opens no connection to a bridge.
- **The tool bridge is checked before a launch**: a refused value or key is `STUDIO-SETTING-REFUSED`, a token absent or shorter than 16 characters `STUDIO-BRIDGE-TOKEN`, and an address with no tool allowed is said without blocking (`STUDIO-BRIDGE-IDLE`).
- **The form screens of the terminal editor scroll.** A screen with more rows than the terminal scrolls, follows the focus and takes the mouse wheel, so every field is reached.
- **The tool catalogue's `system_one_decide` line sends to the Decision models tab.**

## [1.3.0] - 2026-11-18

This release takes the number of the Orkeon release it is built on. On Orkeon `1.3.0`: `OrkeonVersion` moves from `1.2.0` to `1.3.0` (issues #396, #400, #402, #404–#406 and #413–#418), and CI clones the tag `v1.3.0` for the drift tests, which pass on it unchanged. One change in Studio's code follows the forge's new `examples` flag (see Changed); nothing breaks since its 1.2.0.

### Changed

- **The creation assistant runs on Orkeon `1.3.0`'s forge** (Orkeon [#400](https://github.com/Orkeon/orkeon/issues/400)). That forge may propose an input folder with `examples: true`, a folder whose contents change from run to run: the team is then designed for whatever the folder holds when it runs, not for the files found in it. Orkeon 1.3.0's engine carries the proposed value over to a confirmed input only when its name is the same, letter case aside (Orkeon [#419](https://github.com/Orkeon/orkeon/pull/419)), and the user may rename a folder. So Studio, which does not show the property, reads it in `folders.proposed` and sends it back in `folders.confirmed` for each input folder the proposal gave it to (`ForgeFolder.Examples`), through a rename or a role flipped back, and never for an output, where the engine refuses `true`. A folder the proposal said nothing about, or one the user adds, goes back without it, so an older CLI, which never proposes it, reads the line it read before.

## [1.2.0] - 2026-11-17

This release takes the number of the Orkeon release it is built on: there is no Studio 1.1.0. On Orkeon `1.2.0`: `OrkeonVersion` moves from `1.0.0` to `1.2.0` (through `1.1.0`, issues #348–#378, then `1.2.0`, issues #376 and #381–#392), and CI clones the tag `v1.2.0` for the drift tests. The entries that cite Orkeon #387, #388, the run-time half of #392 and the creation assistant's task tools (#392) take effect with a CLI of Orkeon `1.2.0` or later; with an older CLI they change nothing. The pre-launch check of #392 needs no particular CLI: Studio reads the crew with the engine's own loader, from the `Orkeon` package. No breaking change in Studio since its 1.0.0; on a Windows machine that holds several Orkeon CLIs, the one Studio drives may differ (see Changed).

### Added

- **A per-agent `filesystem:` scope the run's mounts refuse is said before the launch** (Orkeon [#349](https://github.com/Orkeon/orkeon/issues/349)). The engine refuses to start an agent whose `filesystem:` entry lies under no mount, asks more than its mount grants, or whose working root lies outside the mounts or the scope; a `--mount` that lowers a root, or a settings entry the run does not mount, provokes it. Studio reads each YAML agent's scope in the layout the loader picks (`CrewFileSystemScopes`) and runs the engine's own check on the effective mounts (`FileSystemScopePreflight`). The verdict follows when the engine refuses: a malformed declaration blocks « Launch now » (« Run » in the TUI launcher) and « Validate (dry-run) » (refused at load); a scope the mounts do not grant blocks « Launch now » only for an agent the run starts for sure, while « Validate (dry-run) » stays offered; an agent the run may not start, or settings Studio cannot read, gets a warning. Which agents start for sure follows the engine's process strategies: under a sequential, parallel or graph process, the agent of each task that runs for sure (no `when:`, no `decision:`, not skipped with its dependencies), which is the agent it names or, when it names none, the only agent of a one-agent crew; a graph that describes its nodes or edges counts its start task alone; under a hierarchical or autonomous process, the crew's only agent, a hierarchical manager set aside, when there is exactly one; under a consensual process, every agent but the manager; the manager never, since no refusal of its scope stops a run. Both launchers read the crew and the settings file again as a launch starts. When a launch passes no `--settings`, the CLI picks the settings file itself, so a refusal there is a warning in the WPF app too, as it was in the TUI launcher. The TUI launcher reports `STUDIO-FS-SCOPE` on the same rules (a warning for a check, or when the CLI resolves the settings file) and lists the refusals with their kind in its mounts dialog.
- **`Llm:ModelCapabilities` is validated as the runtime reads it** (Orkeon [#356](https://github.com/Orkeon/orkeon/issues/356)): a `Thinking` that is not `None`, `EffortOnly`, `Toggle` or `Budget` (a number, an unknown word) and an `AudioInput`, `AudioOutput` or `Vision` that is not a boolean are errors, as they stop the engine at start. So are a list or an object that is not empty where the run reads one value, and a key the run does not know under a model entry: a typo, or a model id that holds a `:` (`llama3.2:latest`), which the configuration splits; the message says to name the entry by the part before it. A blank model id and a key written twice (once the case is ignored and the `:` split) are errors as well. The values of `ReasoningEfforts` are not judged: the runtime takes vendor values.
- **A task that ended on its iteration cap is said so** (Orkeon [#388](https://github.com/Orkeon/orkeon/issues/388)). The engine keeps such a task a success: its agent spent its iterations on tool calls and answered without tools, so a file it had to write may be missing while the run exits `0`. Studio reads the `endedOnIterationCap` flag of `task.completed`: the agent's card reads « Cut short: check its files » in the warning tone, the row of the expert's task table carries a warning icon and a note asking to check its files, the badge of the run reads « Succeeded · 1 task cut short » in the warning tone (after the agents not run, when some were not), and the trial of the creation assistant says « cut short » instead of « done », with a warning icon. The count of the badge is the `cappedTasks` of `run.finished` when the run gives one, else the lines read, each task by its last completion (the creation assistant's trial reads its lines alone, never the count): a task whose retry went through is not said cut short on the Launch screen's cards and badge, nor on the trial's earlier line (the expert's table keeps the note on the attempt that was cut short); a retry that failed, or was cut short again, leaves the trial's earlier line said cut short. The launch history still records such a run as succeeded. A CLI that does not send the flag (Orkeon `1.1.0` and earlier) changes nothing.
- **A task that must write a file without the tool for it is said before the launch** (Orkeon [#392](https://github.com/Orkeon/orkeon/issues/392)). The engine loads a crew whose task delivers by tool call (`deliverable.source: tool_call`, or no source) while no agent that may run it holds a tool that writes that file: the task still succeeds, no file is written and the next task works from an answer cut short. An Orkeon 1.2 CLI warns of it at load; Studio says it before the launch, reading the YAML crew with the engine's own loader (in process, from the `Orkeon` package) and judging it as the engine's `DeliverableToolCheck` does, through that class's helpers: the tool of the file's format counts (`docx_writer` for a `.docx`, `xlsx_writer`, `image_generation`, `firefox` for a `.png`), `file_write` only for a text file, a tool name Studio's catalogue does not carry (an MCP server's, a plugin's) always, though the engine judges a plugin whose assembly is named `Orkeon.*` by its name; `shell_command`, the editors and Orkeon's other tools (`rag_search`, `system_one_decide`, `memory_recall`…) do not. The task is said only when none of the agents that may run it can write — the one it names in a sequential, parallel or graph crew, else every agent; every agent but the manager in a hierarchical or consensual crew; every agent in an autonomous one — and a decision task that declares a deliverable is said too, for a decision writes no file. The launch tab's warning names the task, who cannot write the file and the fix (give the tool of its format, or one that writes it from an MCP server or a plugin; or else `source: final_message` for a text file, a text format for a binary one); the TUI launcher reports it as `STUDIO-DELIVERABLE-WRITER`. It never blocks the run. Nothing is said of a crew the engine's loader or the validator its crew factory runs refuses (Studio calls both): its load error is the one to fix. What the factory judges only against the run's host — a tool name the run does not register, an `llm.profile` the settings lack — is left to the launch, which reports it. A `.ork.ts` crew is left to the CLI.
- **A task that did not write its file is said so** (Orkeon [#392](https://github.com/Orkeon/orkeon/issues/392)). The engine keeps such a task a success: its deliverable is written by tool call, the agent did not write (or update) the file, and the run exits `0`. An Orkeon 1.2 CLI checks the file after the task and says it: Studio reads the `deliverableMissing` flag of `task.completed`, and the `missingDeliverables` count of `run.finished`. The agent's card reads « Did not write its file » in the warning tone, the row of the expert's task table carries a warning icon and a note asking to check that its agent has a tool that writes the file and that the task asks for it (and, for a task cut short too, to give the agent more iterations), the badge of the run reads « Succeeded · 1 task did not write its file » in the warning tone (after the agents not run, when some were not), and the trial of the creation assistant says « done, but did not write its file », with a warning icon, followed by « cut short too: its iterations ran out » for a task cut short as well. The line names no path, so neither does Studio. A file not written takes the badge's place of the tasks cut short, those of other tasks too — the badge says one finding, the fact before the suspicion —, and the card of an agent says it first, then « Cut short: check its files » when one of its tasks was cut short as well, its tooltip giving the note of each; the cards and the table still say every task cut short, and a task cut short whose file was written keeps the cap's texts. The count of the badge is the `missingDeliverables` of `run.finished` when the run gives one, else the lines read, each task by its last completion (the trial reads its lines alone): a task whose retry wrote the file is not said missing it anywhere (the Launch screen's cards, badge and earlier attempt's row, the trial's earlier line); a task whose last attempt failed is not counted on the cards and the badge, and its earlier row, or trial line, keeps its note. The launch history still records such a run as succeeded. A CLI that does not send the fields (Orkeon `1.1.0` and earlier) changes nothing.

### Fixed

- **The tool catalogue of the Settings screen lists every tool a run registers.** The three RAG tools (`rag_search`, `rag_ingest`, `rag_eval`) join Search and knowledge, where `rag_search` says it searches a collection the team's `rag:` block or `rag_ingest` fills, or one the store chosen in the expert Document search (RAG) tab keeps, and `rag_eval` that it needs a golden dataset whose corpus it ingests itself; `memory_recall` joins Session and memory, and two families appear, Decision models (`system_one_decide`) and MCP servers (`mcp_prompt_get`). These three say the condition without which a run does not register them, as the engine reads it: `Orkeon:CognitiveMemory:Enabled = true` written by hand in the settings file, the tool going only to a team with `memory: true`; a decision provider, named by `Orkeon:Decision:Provider` or deduced from an `Orkeon:TypeSafe` or `Orkeon:Liquid` section or from the key `TYPESAFE_API_KEY` or `LIQUID_API_KEY`; Settings › MCP switched on with a server declared. A line that sends to a tab only the expert mode opens says so, and `spawn_agent` says it is offered only in the act of a `.ork.ts` script agent, never to a YAML team. The tools registered under a switch that is on by default (`local_embed_text`, the code analysis tools under `RaggableTree:Enabled`) still say nothing. Tests pin the catalogue to the names of Orkeon's inventory both ways, to the registry a runner host builds, and each condition to the inventory and to the engine's code.
- **A task's reading tools count in the creation assistant's folders** (Orkeon [#392](https://github.com/Orkeon/orkeon/issues/392)). A plan's task may grant its agent tools of its own (`tools:`), and the CLI mounts the read root `/workspace` when an agent's or a task's tools hold `file_read` or `directory_read`. Studio read the agents' alone, so a plan whose reading tool came from a task showed no read folder among its chips and adopted a team whose sidecar mounted none, while the CLI's own derivation had it. The derivation now mirrors the CLI's: a task granting a reading tool names among the readers of `/workspace` (or of the confirmed input folders) every agent that may run it, as the engine's forge reads them — the agent it names under a sequential, parallel or graph process, else every agent; every agent but the manager under a hierarchical or consensual one —, and still mounts the read root when it names no agent the plan declares. A task's deliverable folder is granted the same way to every agent that may write it, and a folder holding `:` or `;`, which the CLI refuses as a mount root, is never derived. The tools a task grants also show among the team's « Can: » chips and on the card of each of those agents, as the CLI's trial counts them among the crew's tools.
- **The endpoint probe speaks each provider's thinking dialect again** (Orkeon [#356](https://github.com/Orkeon/orkeon/issues/356)). Together and Hugging Face send their own switch (`reasoning.enabled`, `chat_template_kwargs.enable_thinking`), MiniMax sends `thinking: {type: disabled}` only to turn it off, Mammouth gets no switch (its gateway takes the effort hint alone: no on/off switch was measured on it), and Anthropic asks the summarized adaptive thinking, with each model's own off value (`between_tools` for `claude-sonnet-5-5`). The switch is narrowed per model as the runtime's capability table narrows it: a model that always reasons (`claude-opus-5-5`, `glm-5.3`, `MiniMax-M3.1-Flash`…) gets no off switch, so the probe no longer sends a request the run would not. A `Thinking` set under `Llm:ModelCapabilities` is merged over that table as the run merges it.
- A `Thinking:Effort` made of blanks is no longer an error: the run reads it as left out. Nor is an empty list or object under a key of `Llm` or of a profile (`Model`, `BaseUrl`, `MaxTokens`, `Thinking:Effort`…), which the configuration reads as a value left out.
- On Linux and macOS, an agent or task file of a per-entity crew whose extension is written in capitals (`.YAML`) is read, as the engine reads it.
- The mounts dialog of the TUI launcher says when a refusal holds only unless the settings the CLI reads mount the folder, as the launcher's own message does.
- **The Diagnostic says how to fix a check Studio cannot fix itself.** « Fix the first issue » and the check's own button used to run the diagnostic again for such a check (a missing tool, a runtime), which showed the same list. They now unfold the advice under the check, in the language of the interface, followed by the engine's own text, in both modes; the check's button reads « How to fix it ». The `tsc` check of `orkeon doctor` has a name, a sentence and an advice of its own.
- The Diagnostic's advice for `tsc` covers what the engine now reports (Orkeon [#387](https://github.com/Orkeon/orkeon/issues/387)): a missing `tsc` that nothing needs is no longer a warning, so the point only shows for a checker that is required and missing, a `TscPath` that does not exist or a `tsc` that does not answer; the advice names the `Orkeon:Scripting:Toolchain:TscPath` setting beside the installation, and the `TypeCheck` setting that makes the checker required.
- The technical journal shows a line the CLI leads with `WARNING: ` in the colour of a warning, no longer as an error (or in the colour of the line before it): `orkeon run --validate` writes that way, to stderr without a level, the findings of a load it does not refuse, such as Orkeon [#392](https://github.com/Orkeon/orkeon/issues/392)'s task whose file no agent can write, beside a validation that passed.
- The technical journal shows the CLI's « Using settings: … » line in the colour of a success, no longer as an error: it reaches stderr without a log level.
- The status bar hears the token meter on the UI thread. At the end of a rephrase in the creation assistant, the balance entries were rebuilt from a pool thread: WPF refused the change, the exception was swallowed and the balance was not read again.
- The profile help texts list the effort levels `low` to `max` and say that a level the model does not take is lowered, and that a model that always reasons ignores « Off », each with a warning.
- **The CLI installed by the Orkeon Windows installers is found without `ORKEON_CLI_DIR`** ([#5](https://github.com/Orkeon/orkeon-studio/issues/5)). Those installers (the MSI, or the zip's `install.ps1`) put `bin\orkeon.cmd` on `PATH` and the real `orkeon.exe` in `libexec\orkeon`, which Studio's `orkeon.exe`-only lookup never reached. On Windows the lookup now follows a `bin\orkeon.cmd` found on `PATH` to its `..\libexec\orkeon\orkeon.exe`, at that `PATH` entry's rank, then tries the installers' default folder `%LOCALAPPDATA%\Programs\Orkeon\libexec\orkeon` after `PATH` (a `PATH` inherited before the install, or trimmed). Either hit reports the new `BinarySource.OrkeonInstaller`. A `bin` folder named with `--cli-dir` or `ORKEON_CLI_DIR` is followed the same way, and both keep their precedence. The "CLI not found" message lists both new steps.
- **A `.ork.ts` crew finds the esbuild of an Orkeon install.** Only the `bin\orkeon.cmd` launcher points the CLI at the esbuild shipped in `libexec\esbuild-bin` (`ORKEON_ESBUILD_PATH`); Studio runs `libexec\orkeon\orkeon.exe` directly, so the CLI found no compiler, and the Diagnostic reported it missing. The same gap hit the `ORKEON_CLI_DIR` workaround and a Studio installed inside the CLI's tree. `BinaryLocation.LaunchEnvironment` now carries that variable whenever the binary sits in `libexec/orkeon` beside a `libexec/esbuild-bin` esbuild and the variable is unset, and every launch (run, doctor, forge) passes it; a variable the caller sets still wins.
- The README shipped in the Windows zip and MSI no longer asks for `ORKEON_CLI_DIR` after an Orkeon installer; it, the MSI's closing dialog and the release notes name the Orkeon installers as a way to get the CLI.

### Changed

- **No build downloads the local embeddings model** (Orkeon [#368](https://github.com/Orkeon/orkeon/issues/368)). `Orkeon.Scripting`, which `Orkeon.Studio.Core.Tests` references, lets the `SmartComponents.LocalEmbeddings` build target reach its consumers: that target downloads the BGE-micro-v2 weights (~17 MB) from huggingface.co on a first build, and fails an offline one. No Studio project embeds anything, so `Orkeon.Studio.Core.Tests` references `Orkeon.Scripting` with `ExcludeAssets="build"`, the opt-out Orkeon `1.2.0` supports ([#376](https://github.com/Orkeon/orkeon/issues/376)): nothing is downloaded or copied to `LocalEmbeddingsModel/`.
- On a Windows machine that also has an Orkeon install, a Studio started from a development checkout now drives the installed CLI rather than the one built in the Orkeon checkout (`ORKEON_SOURCE_ROOT` or `../orkeon`), as a CLI on `PATH` (the .NET tool, or Linux packages) already did. To drive the checkout's build, name the directory that holds its `orkeon.exe` with `--cli-dir` (WPF app) or `ORKEON_CLI_DIR`.
- On a Windows machine that has both an Orkeon install and another `orkeon.exe` on `PATH` (the .NET tool), Studio drives the one whose folder comes first on `PATH`; before, it saw the `orkeon.exe` alone, whatever the order. An `ORKEON_CLI_DIR` or `--cli-dir` that names an Orkeon install's `bin` folder, ignored before, now wins over `PATH`.

## [1.0.0-rc.8] - 2026-11-12

### Orkeon from nuget.org

Studio now builds against Orkeon `1.0.0` from nuget.org: the local `orkeon-feed/` source is gone from `nuget.config`.

- `OrkeonVersion` in `Directory.Packages.props` is a published version; CI and the release pipeline clone the Orkeon tag `v<OrkeonVersion>` for the drift tests. `.github/orkeon-source-ref` and `scripts/pack-orkeon-feed.sh` are removed.
- `scripts/install-from-source.*` still pack an Orkeon checkout into `orkeon-feed/`, and now restore through a `nuget.config` they write in their stage folder.
- A plain build of the checkout no longer reads `orkeon-feed/`: a local build against unpublished Orkeon packages goes through `scripts/install-from-source.*`.
- **Team sidecar** **[breaking]**: Orkeon 1.0.0-rc.7 names it `team.json` (`ConventionalNames.TeamSidecarFile`) and no longer reads `studio-team.json`. Studio follows; the catalog renames a `studio-team.json` it meets without a `team.json` beside it, bytes untouched, so a team adopted before keeps its name, need, profile and folders. A disk that refuses the rename leaves the old file read and written in place.
- The launchers Studio writes say `team.json` in their note line; Orkeon no longer carries Studio's note (`TeamLauncherSpec.WrittenByStudio` became `WriterNote`), Studio passes its own (`TeamLaunchers.WriterNote`).
- `ORKEON_CLI_DIR`, `ORKEON_CUSTOM_LLM_API_KEY` and `ORKEON_STUDIO_TEAMS_ROOT` left Orkeon's `EnvironmentVariableNames`: Studio defines them itself, unchanged.
- Orkeon 1.0.0 keeps `AcceptHandlers` (Orkeon.Cli.TerminalGui) internal: the Terminal.Gui apps carry their own `OnAccept`. `LlmPresets.DockerModelRunnerDefaultModel` is `static readonly`, like the Orkeon model id it copies.
- The Email and Drive oracle and drift tests of `Orkeon.Studio.Core.Tests` reach the engine's internal option types through `Krafs.Publicizer` (test project only), Orkeon no longer opening them to Studio.

### Own release pipeline

Orkeon Studio is released from this repository, on its own version, and no longer through Orkeon's installers. The `orkeon` CLI becomes a prerequisite installed separately (`dotnet tool install -g Orkeon.Scripting.Cli`, or Orkeon's installers).

- A `v*` tag runs `.github/workflows/release.yml`: it refuses a tag that does not match `src/Directory.Build.props`, builds and tests, packages, smokes on Windows and Linux, then attaches the assets and one `SHA256SUMS` to a draft GitHub Release (marked prerelease when the version has a suffix).
- Assets: `orkeon-studio-<version>-win-x64.zip` and `orkeon-studio-<version>-win-x64.msi` (the WPF app; per-user MSI in `%LOCALAPPDATA%\Programs\Orkeon Studio` with a Start-menu shortcut, its own UpgradeCode), and `orkeon-studio-<version>-linux-x64.tar.gz` (`orkeon-studio-config` and `orkeon-studio-run`). Every app is self-contained, untrimmed, not single-file, as Orkeon published them.
- `scripts/package-studio.sh` builds the archives, `scripts/build-msi.ps1` the MSI (WiX v5, pinned in `.config/dotnet-tools.json`), `scripts/smoke-studio-linux.sh` and `scripts/smoke-studio-windows.ps1` smoke them.
- Studio no longer finds the CLI next to itself in an Orkeon install: on Windows, a user of Orkeon's installers sets `ORKEON_CLI_DIR` to its `libexec\orkeon` folder (the .NET tool needs nothing).

### Extracted from Orkeon

Orkeon Studio now lives in its own repository. The four projects (`Orkeon.Studio.Core`, `Orkeon.Studio.Config`, `Orkeon.Studio.Run`, `Orkeon.Studio.Wpf`) and their four test projects were copied from the Orkeon repository as a snapshot, without history.

- Orkeon is consumed through NuGet packages instead of project references: `Orkeon`, `Orkeon.Constants.Cli`, `Orkeon.Cli.Abstractions`, `Orkeon.Cli.TerminalGui`, the `Orkeon.Compliance.Vfs` analyzer, and, for the tests only, `Orkeon.Tools` and `Orkeon.Scripting`. One `OrkeonVersion` property in `Directory.Packages.props` sets their version.
- `Orkeon.Studio.Core` now references the `Orkeon` umbrella package, which carries `Orkeon.Infrastructure` and its dependencies, where it used to reference only `Orkeon.Domain`, `Orkeon.Rag.Abstractions` and the `Orkeon.Constants.*` satellites: a self-contained publish is heavier until Orkeon ships slimmer packages.
- The drift tests that read files Orkeon ships but does not package now read them from an Orkeon checkout named by `ORKEON_SOURCE_ROOT`, or `../orkeon`.
- The shared test fixtures Studio uses were copied from `Orkeon.Tests.Shared` into `Orkeon.Studio.Tests.Shared`, namespaces unchanged.
- Studio has its own version (`VersionPrefix`/`VersionSuffix` in `src/Directory.Build.props`), independent of Orkeon's.
- `scripts/install-from-source.sh` (Linux, macOS) and `scripts/install-from-source.ps1` (Windows) install Studio from a clone into an Orkeon CLI's installation, where Studio finds the CLI next to itself, optionally installing that CLI first from an Orkeon checkout.
- The local Orkeon feed moved from `../orkeon-feed` to `orkeon-feed/` at the repository root (git-ignored): move or re-pack your packages there, or the restore fails.
