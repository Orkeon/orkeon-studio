# Changelog

All notable changes to Orkeon Studio are recorded here. Breaking changes come first in each release, with a migration table when one applies.

## Unreleased

On Orkeon `1.2.0`: `OrkeonVersion` moves from `1.0.0` to `1.2.0` (through `1.1.0`, issues #348–#378, then `1.2.0`, issues #376 and #381–#392), and CI clones the tag `v1.2.0` for the drift tests. The entries that cite Orkeon #387, #388, the run-time half of #392 and the creation assistant's task tools (#392) take effect with a CLI of Orkeon `1.2.0` or later; with an older CLI they change nothing. The pre-launch check of #392 needs no particular CLI: Studio reads the crew with the engine's own loader, from the `Orkeon` package. No breaking change in Studio since its 1.0.0.

### Added

- **A per-agent `filesystem:` scope the run's mounts refuse is said before the launch** (Orkeon [#349](https://github.com/Orkeon/orkeon/issues/349)). The engine refuses to start an agent whose `filesystem:` entry lies under no mount, asks more than its mount grants, or whose working root lies outside the mounts or the scope; a `--mount` that lowers a root, or a settings entry the run does not mount, provokes it. Studio reads each YAML agent's scope in the layout the loader picks (`CrewFileSystemScopes`) and runs the engine's own check on the effective mounts (`FileSystemScopePreflight`). The verdict follows when the engine refuses: a malformed declaration blocks « Launch now » (« Run » in the TUI launcher) and « Validate (dry-run) » (refused at load); a scope the mounts do not grant blocks « Launch now » only for an agent the run starts for sure, while « Validate (dry-run) » stays offered; an agent the run may not start, or settings Studio cannot read, gets a warning. Which agents start for sure follows the engine's process strategies: under a sequential, parallel or graph process, the agent of each task that runs for sure (no `when:`, no `decision:`, not skipped with its dependencies), which is the agent it names or, when it names none, the only agent of a one-agent crew; a graph that describes its nodes or edges counts its start task alone; under a hierarchical or autonomous process, the crew's only agent, a hierarchical manager set aside, when there is exactly one; under a consensual process, every agent but the manager; the manager never, since no refusal of its scope stops a run. Both launchers read the crew and the settings file again as a launch starts. When a launch passes no `--settings`, the CLI picks the settings file itself, so a refusal there is a warning in the WPF app too, as it was in the TUI launcher. The TUI launcher reports `STUDIO-FS-SCOPE` on the same rules (a warning for a check, or when the CLI resolves the settings file) and lists the refusals with their kind in its mounts dialog.
- **`Llm:ModelCapabilities` is validated as the runtime reads it** (Orkeon [#356](https://github.com/Orkeon/orkeon/issues/356)): a `Thinking` that is not `None`, `EffortOnly`, `Toggle` or `Budget` (a number, an unknown word) and an `AudioInput`, `AudioOutput` or `Vision` that is not a boolean are errors, as they stop the engine at start. So are a list or an object that is not empty where the run reads one value, and a key the run does not know under a model entry: a typo, or a model id that holds a `:` (`llama3.2:latest`), which the configuration splits; the message says to name the entry by the part before it. A blank model id and a key written twice (once the case is ignored and the `:` split) are errors as well. The values of `ReasoningEfforts` are not judged: the runtime takes vendor values.
- **A task that ended on its iteration cap is said so** (Orkeon [#388](https://github.com/Orkeon/orkeon/issues/388)). The engine keeps such a task a success: its agent spent its iterations on tool calls and answered without tools, so a file it had to write may be missing while the run exits `0`. Studio reads the `endedOnIterationCap` flag of `task.completed`: the agent's card reads « Cut short: check its files » in the warning tone, the row of the expert's task table carries a warning icon and a note asking to check its files, the badge of the run reads « Succeeded · 1 task cut short » in the warning tone (after the agents not run, when some were not), and the trial of the creation assistant says « cut short » instead of « done », with a warning icon. The count of the badge is the `cappedTasks` of `run.finished` when the run gives one, else the lines read, each task by its last completion: a task whose retry went through is not said cut short, on the Launch screen's cards and badge as in the trial (the expert's table keeps the note on the attempt that was cut short). The launch history still records such a run as succeeded. A CLI that does not send the flag (Orkeon `1.1.0` and earlier) changes nothing.
- **A task that must write a file without the tool for it is said before the launch** (Orkeon [#392](https://github.com/Orkeon/orkeon/issues/392)). The engine loads a crew whose task delivers by tool call (`deliverable.source: tool_call`, or no source) while no agent that may run it holds a tool that writes that file: the task still succeeds, no file is written and the next task works from an answer cut short. An Orkeon 1.2 CLI warns of it at load; Studio says it before the launch, reading the YAML crew with the engine's own loader (in process, from the `Orkeon` package) and judging it as the engine's `DeliverableToolCheck` does, through that class's helpers: the tool of the file's format counts (`docx_writer` for a `.docx`, `xlsx_writer`, `image_generation`, `firefox` for a `.png`), `file_write` only for a text file, a tool name Studio's catalogue does not carry (an MCP server's, a plugin's) always, though the engine judges a plugin whose assembly is named `Orkeon.*` by its name; `shell_command`, the editors and Orkeon's other tools (`rag_search`, `system_one_decide`, `memory_recall`…) do not. The task is said only when none of the agents that may run it can write — the one it names in a sequential, parallel or graph crew, else every agent; every agent but the manager in a hierarchical or consensual crew; every agent in an autonomous one — and a decision task that declares a deliverable is said too, for a decision writes no file. The launch tab's warning names the task, who cannot write the file and the fix (give the tool of its format, or one that writes it from an MCP server or a plugin; or else `source: final_message` for a text file, a text format for a binary one); the TUI launcher reports it as `STUDIO-DELIVERABLE-WRITER`. It never blocks the run. Nothing is said of a crew the engine's loader or the validator its crew factory runs refuses (Studio calls both): its load error is the one to fix. What the factory judges only against the run's host — a tool name the run does not register, an `llm.profile` the settings lack — is left to the launch, which reports it. A `.ork.ts` crew is left to the CLI.
- **A task that did not write its file is said so** (Orkeon [#392](https://github.com/Orkeon/orkeon/issues/392)). The engine keeps such a task a success: its deliverable is written by tool call, the agent did not write (or update) the file, and the run exits `0`. An Orkeon 1.2 CLI checks the file after the task and says it: Studio reads the `deliverableMissing` flag of `task.completed`, and the `missingDeliverables` count of `run.finished`. The agent's card reads « Did not write its file » in the warning tone, the row of the expert's task table carries a warning icon and a note asking to check that its agent has a tool that writes the file and that the task asks for it (and, for a task cut short too, to give the agent more iterations), the badge of the run reads « Succeeded · 1 task did not write its file » in the warning tone (after the agents not run, when some were not), and the trial of the creation assistant says « done, but did not write its file », with a warning icon. The line names no path, so neither does Studio. A file not written takes the badge's place of the tasks cut short — one finding a task, the fact before the suspicion —, and the card of an agent says it first, then « Cut short: check its files » when one of its tasks was cut short as well; the cards and the table still say every task cut short, and a task cut short whose file was written keeps the cap's texts. The count of the badge is the `missingDeliverables` of `run.finished` when the run gives one, else the lines read, each task by its last completion: a task whose retry wrote the file, or a failed one, is not said missing it, on the Launch screen (cards, badge and the earlier attempt's row) as in the trial. The launch history still records such a run as succeeded. A CLI that does not send the fields (Orkeon `1.1.0` and earlier) changes nothing.

### Fixed

- **The tool catalogue of the Settings screen lists every tool a run registers.** The three RAG tools (`rag_search`, `rag_ingest`, `rag_eval`) join Search and knowledge, where `rag_search` says it searches a collection the team's `rag:` block or `rag_ingest` fills, or one the store chosen in the expert Document search (RAG) tab keeps, and `rag_eval` that it needs a golden dataset whose corpus it ingests itself; `memory_recall` joins Session and memory, and two families appear, Decision models (`system_one_decide`) and MCP servers (`mcp_prompt_get`). These three say the condition without which a run does not register them, as the engine reads it: `Orkeon:CognitiveMemory:Enabled = true` written by hand in the settings file, the tool going only to a team with `memory: true`; a decision provider, named by `Orkeon:Decision:Provider` or deduced from an `Orkeon:TypeSafe` or `Orkeon:Liquid` section or from the key `TYPESAFE_API_KEY` or `LIQUID_API_KEY`; Settings › MCP switched on with a server declared. A line that sends to a tab only the expert mode opens says so, and `spawn_agent` says it is offered only in the act of a `.ork.ts` script agent, never to a YAML team. The tools registered under a switch that is on by default (`local_embed_text`, the code analysis tools under `RaggableTree:Enabled`) still say nothing. Tests pin the catalogue to the names of Orkeon's inventory both ways, to the registry a runner host builds, and each condition to the inventory and to the engine's code.
- **A task's reading tools count in the creation assistant's folders** (Orkeon [#392](https://github.com/Orkeon/orkeon/issues/392)). A plan's task may grant its agent tools of its own (`tools:`), and the CLI mounts the read root `/workspace` when an agent's or a task's tools hold `file_read` or `directory_read`. Studio read the agents' alone, so a plan whose reading tool came from a task showed no read folder among its chips and adopted a team whose sidecar mounted none, while the CLI's own derivation had it. The derivation now mirrors the CLI's: a task granting a reading tool names its agent among the readers of `/workspace` (or of the confirmed input folders), and still mounts the read root when it names no agent the plan declares. The tools a task grants also show among the team's « Can: » chips and on the card of its agent, as the CLI's trial counts them among the crew's tools.
- **The endpoint probe speaks each provider's thinking dialect again** (Orkeon [#356](https://github.com/Orkeon/orkeon/issues/356)). Together and Hugging Face send their own switch (`reasoning.enabled`, `chat_template_kwargs.enable_thinking`), MiniMax sends `thinking: {type: disabled}` only to turn it off, Mammouth gets no switch (its models always reason), and Anthropic asks the summarized adaptive thinking, with each model's own off value (`between_tools` for `claude-sonnet-5-5`). The switch is narrowed per model as the runtime's capability table narrows it: a model that always reasons (`claude-opus-5-5`, `glm-5.3`, `MiniMax-M3.1-Flash`…) gets no off switch, so the probe no longer sends a request the run would not. A `Thinking` set under `Llm:ModelCapabilities` is merged over that table as the run merges it.
- A `Thinking:Effort` made of blanks is no longer an error: the run reads it as left out. Nor is an empty list or object under a key of `Llm` or of a profile (`Model`, `BaseUrl`, `MaxTokens`, `Thinking:Effort`…), which the configuration reads as a value left out.
- On Linux and macOS, an agent or task file of a per-entity crew whose extension is written in capitals (`.YAML`) is read, as the engine reads it.
- The mounts dialog of the TUI launcher says when a refusal holds only unless the settings the CLI reads mount the folder, as the launcher's own message does.
- **The Diagnostic says how to fix a check Studio cannot fix itself.** « Fix the first issue » and the check's own button used to run the diagnostic again for such a check (a missing tool, a runtime), which showed the same list. They now unfold the advice under the check, in the language of the interface, followed by the engine's own text, in both modes; the check's button reads « How to fix it ». The `tsc` check of `orkeon doctor` has a name, a sentence and an advice of its own.
- The Diagnostic's advice for `tsc` covers what the engine now reports (Orkeon [#387](https://github.com/Orkeon/orkeon/issues/387)): a missing `tsc` that nothing needs is no longer a warning, so the point only shows for a checker that is required and missing, a `TscPath` that does not exist or a `tsc` that does not answer; the advice names the `Orkeon:Scripting:Toolchain:TscPath` setting beside the installation, and the `TypeCheck` setting that makes the checker required.
- The technical journal shows the CLI's « Using settings: … » line in the colour of a success, no longer as an error: it reaches stderr without a log level.
- The status bar hears the token meter on the UI thread. At the end of a rephrase in the creation assistant, the balance entries were rebuilt from a pool thread: WPF refused the change, the exception was swallowed and the balance was not read again.
- The profile help texts list the effort levels `low` to `max` and say that a level the model does not take is lowered, and that a model that always reasons ignores « Off », each with a warning.
- **The CLI installed by the Orkeon Windows installers is found without `ORKEON_CLI_DIR`** ([#5](https://github.com/Orkeon/orkeon-studio/issues/5)). Those installers (the MSI, or the zip's `install.ps1`) put `bin\orkeon.cmd` on `PATH` and the real `orkeon.exe` in `libexec\orkeon`, which Studio's `orkeon.exe`-only lookup never reached. On Windows the lookup now follows a `bin\orkeon.cmd` found on `PATH` to its `..\libexec\orkeon\orkeon.exe`, at that `PATH` entry's rank, then tries the installers' default folder `%LOCALAPPDATA%\Programs\Orkeon\libexec\orkeon` after `PATH` (a `PATH` inherited before the install, or trimmed). Either hit reports the new `BinarySource.OrkeonInstaller`. A `bin` folder named with `--cli-dir` or `ORKEON_CLI_DIR` is followed the same way, and both keep their precedence. The "CLI not found" message lists both new steps.
- **A `.ork.ts` crew finds the esbuild of an Orkeon install.** Only the `bin\orkeon.cmd` launcher points the CLI at the esbuild shipped in `libexec\esbuild-bin` (`ORKEON_ESBUILD_PATH`); Studio runs `libexec\orkeon\orkeon.exe` directly, so the CLI found no compiler, and the Diagnostic reported it missing. The same gap hit the `ORKEON_CLI_DIR` workaround and a Studio installed inside the CLI's tree. `BinaryLocation.LaunchEnvironment` now carries that variable whenever the binary sits in `libexec/orkeon` beside a `libexec/esbuild-bin` esbuild and the variable is unset, and every launch (run, doctor, forge) passes it; a variable the caller sets still wins.
- The README shipped in the Windows zip and MSI, the MSI's closing dialog and the release notes no longer ask for `ORKEON_CLI_DIR` after an Orkeon installer, and name the Orkeon installers as a way to get the CLI.

### Changed

- **No build downloads the local embeddings model** (Orkeon [#368](https://github.com/Orkeon/orkeon/issues/368)). `Orkeon.Scripting`, which `Orkeon.Studio.Core.Tests` references, lets the `SmartComponents.LocalEmbeddings` build target reach its consumers: that target downloads the BGE-micro-v2 weights (~17 MB) from huggingface.co on a first build, and fails an offline one. No Studio project embeds anything, so `Orkeon.Studio.Core.Tests` references `Orkeon.Scripting` with `ExcludeAssets="build"`, the opt-out Orkeon `1.2.0` supports ([#376](https://github.com/Orkeon/orkeon/issues/376)): nothing is downloaded or copied to `LocalEmbeddingsModel/`.
- On a Windows machine that also has an Orkeon install, a Studio started from a development checkout now drives the installed CLI rather than the one built in the Orkeon checkout (`ORKEON_SOURCE_ROOT` or `../orkeon`), as a CLI on `PATH` (the .NET tool, or Linux packages) already did. To drive the checkout's build, name its directory with `--cli-dir` (WPF app) or `ORKEON_CLI_DIR`.

## [1.0.0] - 2026-11-12

First stable release, on Orkeon `1.0.0`. No breaking change since 1.0.0-rc.8.

### Fixed

- **WPF binding errors** on "My teams", the diagnostic view and the help panel of "Create a team" (`Cannot find source for binding with reference 'RelativeSource FindAncestor'`): the content slots of the controls (`Alert.Actions`, `PropertyRow.Action`, `EmptyState.Actions`, `StepTabs.SideContent`) are now logical children of their control, so their bindings resolve while the control is collapsed. A team card's "Not now" on the archive suggestion binds to the card's own `DismissSuggestionCommand`.

## [1.0.0-rc.8] - 2026-11-12

### Orkeon from nuget.org

Studio now builds against Orkeon `1.0.0` from nuget.org: the local `orkeon-feed/` source is gone from `nuget.config`.

- `OrkeonVersion` in `Directory.Packages.props` is a published version; CI and the release pipeline clone the Orkeon tag `v<OrkeonVersion>` for the drift tests. `.github/orkeon-source-ref` and `scripts/pack-orkeon-feed.sh` are removed.
- `scripts/install-from-source.*` still pack an Orkeon checkout into `orkeon-feed/`, and now restore through a `nuget.config` they write in their stage folder.
- A plain build of the checkout no longer reads `orkeon-feed/`: a local build against unpublished Orkeon packages goes through `scripts/install-from-source.*`.
- **Team sidecar** **[breaking]**: Orkeon 1.0.0-rc.7 names it `team.json` (`ConventionalNames.TeamSidecarFile`) and no longer reads `studio-team.json`. Studio follows; the catalog renames a `studio-team.json` it meets without a `team.json` beside it, bytes untouched, so a team adopted before keeps its name, need, profile and folders. A disk that refuses the rename leaves the old file read and written in place.
- The launchers Studio writes say `team.json` in their note line; Orkeon no longer carries Studio's note (`TeamLauncherSpec.WrittenByStudio` became `WriterNote`), Studio passes its own (`TeamLaunchers.WriterNote`).
- `ORKEON_CLI_DIR`, `ORKEON_CUSTOM_LLM_API_KEY` and `ORKEON_STUDIO_TEAMS_ROOT` left Orkeon's `EnvironmentVariableNames`: Studio defines them itself, unchanged.
- Orkeon 1.0.0 keeps `AcceptHandlers` (Orkeon.Cli.TerminalGui) internal: the Terminal.Gui apps carry their own `OnAccept`. `LlmPresets.DockerModelRunnerDefaultModel` is `static readonly`, like the Orkeon model id it copies.
- The Email and Drive oracle and drift tests of `Orkeon.Studio.Core.Tests` reach the engine's internal option types through `Krafs.Publicizer` (test project only), Orkeon no longer opening them to Studio.

### Own release pipeline

Orkeon Studio is released from this repository, on its own version, and no longer through Orkeon's installers. The `orkeon` CLI becomes a prerequisite installed separately (`dotnet tool install -g Orkeon.Scripting.Cli`, or Orkeon's installers).

- A `v*` tag runs `.github/workflows/release.yml`: it refuses a tag that does not match `src/Directory.Build.props`, builds and tests, packages, smokes on Windows and Linux, then attaches the assets and one `SHA256SUMS` to a draft GitHub Release (marked prerelease when the version has a suffix).
- Assets: `orkeon-studio-<version>-win-x64.zip` and `orkeon-studio-<version>-win-x64.msi` (the WPF app; per-user MSI in `%LOCALAPPDATA%\Programs\Orkeon Studio` with a Start-menu shortcut, its own UpgradeCode), and `orkeon-studio-<version>-linux-x64.tar.gz` (`orkeon-studio-config` and `orkeon-studio-run`). Every app is self-contained, untrimmed, not single-file, as Orkeon published them.
- `scripts/package-studio.sh` builds the archives, `scripts/build-msi.ps1` the MSI (WiX v5, pinned in `.config/dotnet-tools.json`), `scripts/smoke-studio-linux.sh` and `scripts/smoke-studio-windows.ps1` smoke them.
- Studio no longer finds the CLI next to itself in an Orkeon install: on Windows, a user of Orkeon's installers sets `ORKEON_CLI_DIR` to its `libexec\orkeon` folder (the .NET tool needs nothing).

### Extracted from Orkeon

Orkeon Studio now lives in its own repository. The four projects (`Orkeon.Studio.Core`, `Orkeon.Studio.Config`, `Orkeon.Studio.Run`, `Orkeon.Studio.Wpf`) and their four test projects were copied from the Orkeon repository as a snapshot, without history.

- Orkeon is consumed through NuGet packages instead of project references: `Orkeon`, `Orkeon.Constants.Cli`, `Orkeon.Cli.Abstractions`, `Orkeon.Cli.TerminalGui`, the `Orkeon.Compliance.Vfs` analyzer, and, for the tests only, `Orkeon.Tools` and `Orkeon.Scripting`. One `OrkeonVersion` property in `Directory.Packages.props` sets their version.
- `Orkeon.Studio.Core` now references the `Orkeon` umbrella package, which carries `Orkeon.Infrastructure` and its dependencies, where it used to reference only `Orkeon.Domain`, `Orkeon.Rag.Abstractions` and the `Orkeon.Constants.*` satellites: a self-contained publish is heavier until Orkeon ships slimmer packages.
- The drift tests that read files Orkeon ships but does not package now read them from an Orkeon checkout named by `ORKEON_SOURCE_ROOT`, or `../orkeon`.
- The shared test fixtures Studio uses were copied from `Orkeon.Tests.Shared` into `Orkeon.Studio.Tests.Shared`, namespaces unchanged.
- Studio has its own version (`VersionPrefix`/`VersionSuffix` in `src/Directory.Build.props`), independent of Orkeon's.
- `scripts/install-from-source.sh` (Linux, macOS) and `scripts/install-from-source.ps1` (Windows) install Studio from a clone into an Orkeon CLI's installation, where Studio finds the CLI next to itself, optionally installing that CLI first from an Orkeon checkout.
- The local Orkeon feed moved from `../orkeon-feed` to `orkeon-feed/` at the repository root (git-ignored): move or re-pack your packages there, or the restore fails.
